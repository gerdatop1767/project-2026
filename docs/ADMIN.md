# Админ-панель «Зубрилки»

Панель владельца проекта по адресу `https://zybrilka.ru/admin`. Она доступна **только владельцу**. Доступ проверяет сервер на каждом запросе.

## 1. Доступ (owner-only)

### Как назначается владелец

Владелец задаётся переменной окружения API **`ADMIN_OWNER_USER_IDS`**. Значение — `id` уже существующей записи в таблице `users`; можно указать до 5 через запятую.

- По умолчанию переменная пустая, и тогда **админа нет ни у кого**.
- Значение, которое не является UUID, останавливает запуск API с понятной ошибкой. Такую ошибку нельзя молча проглотить.
- Ни регистрация, ни вход, ни какой-либо запрос не может добавить id в этот список. В интерфейсе нет способа «сделать себя админом».

### Назначение владельца на сервере

1. Войдите на сайт своим аккаунтом (VK ID, Telegram или почта).
2. Узнайте свой id. Подключитесь к базе (`docker compose exec postgres psql -U $POSTGRES_USER $POSTGRES_DB`) и найдите его, например, по своему VK id:

   ```sql
   SELECT user_id FROM auth_identities WHERE provider = 'vk' AND provider_user_id = '<ваш VK id>';
   ```

   Для Telegram используйте `provider = 'telegram'`, для почты — `provider = 'email'` и адрес в нижнем регистре.
3. Пропишите id в `infra/.env` на сервере: `ADMIN_OWNER_USER_IDS=<id>`. В репозиторий его не коммитьте.
4. Перезапустите контейнер API: `docker compose up -d api`.

### Что проверяется на сервере

Код: `apps/api/src/modules/admin/access.ts`.

| Ситуация | Ответ |
|---|---|
| Нет действительной сессии (httpOnly-cookie `session_id`, проверяется по `auth_sessions`) | **401** |
| Сессия есть, но пользователь не в списке | **403**, попытка пишется в журнал аудита |
| Изменение данных без заголовка `x-zybrilka-admin: 1` | **403**. Кросс-сайтовая страница не может отправить этот заголовок без CORS-preflight, а API его не разрешает |
| Изменение данных с `Sec-Fetch-Site: cross-site` | **403** |

Дополнительно:
- лимит 240 запросов в минуту на аккаунт;
- `Cache-Control: no-store`;
- ошибки 5xx возвращаются без подробностей (`internal_error`).

Заголовки `x-anon-id` и `x-user-id`, параметры запроса, cookie с id владельца и флаги в браузере **ни на что не влияют**: это покрыто тестами.

Изменения, которые затрагивают пользователей, сервер выполняет только с `confirm: true`, а интерфейс перед ними спрашивает подтверждение. Таких изменений три:
- статус задания;
- отключение или архив кампании;
- завершение сессий пользователя.

2FA отдельно не добавлена: вход идёт через VK ID, Telegram или почту, и второй фактор обеспечивает провайдер (например, 2FA в VK). Собственную криптографию мы не пишем.

## 2. Определения метрик

| Понятие | Как считается |
|---|---|
| Зарегистрированный пользователь | Запись `users`, у которой есть хотя бы одна идентичность входа (`auth_identities`). Анонимные записи времён до авторизации пользователями не считаются; их число показано отдельно |
| Гость | Браузер (или WebView Telegram) со случайным id в httpOnly-cookie `zv`. Это не человек, и он никогда не становится «пользователем» |
| Проверенный ответ | Строка `attempts` у зарегистрированного (история с запуска) или событие `answer_checked` без пользователя у гостя (только с начала сбора событий) |
| Активный (DAU/WAU/MAU) | Хотя бы один проверенный ответ за последний день, 7 или 30 дней, заканчивающихся последним днём периода. Зарегистрированные и гости считаются отдельно |
| Решённое задание | Уникальная пара (пользователь, задание), в которой есть хотя бы один верный ответ |
| Повтор | Ответ сверх первого у того же пользователя на то же задание |
| Вернувшийся | Активен в интервале и был активен в какой-то день до него |
| Регистрация | Время создания аккаунта (`users.created_at`); способ — первая идентичность |

Общие правила:
- **Дни** — календарные дни по Москве (UTC+3, без перехода на летнее время).
- **Сравнение** — с периодом той же длины непосредственно перед выбранным. Если база сравнения равна 0, показывается «нет базы для сравнения», а не 0% и не ∞.
- **Неизвестное значение** показывается как «нет данных», никогда как 0.

## 3. События (собираются с момента выкладки)

Таблица `analytics_events`. Каждое событие содержит id, тип, время, посетителя и/или пользователя, предмет или задание, кампанию и пару служебных полей в `props`.

Никогда не хранятся:
- введённые ответы;
- IP-адреса;
- user agent;
- query-строки;
- секреты.

Повтор не засчитывается дважды: у клиентских событий ключ `dedup_key` — это их случайный id, у серверных — естественный ключ (id попытки, регистрации или жалобы).

| Событие | Источник |
|---|---|
| `visit` | Клиент, один раз на загрузку приложения |
| `subject_selected` | Клиент, при смене предмета |
| `task_started` | Клиент, при открытии задания |
| `training_completed` | Клиент, при завершении умной тренировки или варианта |
| `answer_checked` | Сервер, при проверке ответа (гость или пользователь) |
| `registration_completed` / `login_completed` | Сервер, при входе |
| `campaign_click` | Сервер, при переходе по ссылке кампании или запуске Mini App с `startapp` |
| `complaint_submitted` | Сервер |

`page_view` отдельно не пишется, его роль выполняет `visit`. `return_session_started` не пишется: возврат вычисляется по дням активности.

## 4. Кампании и атрибуция

- **Ссылка кампании.** Обычная ссылка имеет вид `https://zybrilka.ru/api/v1/go/<метка>`. Для Mini App используется `https://t.me/<бот>?startapp=<метка>`.
- **Переход.** Открытие ссылки засчитывается как переход. Боты превью ссылок (TelegramBot, vkShare и другие) не засчитываются.
- **Нет открытого редиректа.** Целью может быть только страница этого сайта из фиксированного списка, адрес строится от `WEB_BASE_URL`. Отключённая, архивная или неизвестная метка ведёт на главную, и переход не засчитывается.
- **First touch.** Браузер запоминает первую кампанию. Касание старше **30 дней** не используется, а следующая кампания перезаписывает его.
- **Регистрация** приписывается кампании, только если аккаунт создан в том же браузере, где открыли ссылку, и не позже 30 дней после касания.
- **Не связываются:** браузер с Telegram Mini App и разные устройства. В этих случаях источник регистрации — «неизвестно».
- **Повторные клики** считаются в «переходах», а в «уникальных посетителях» учитываются один раз.
- **Органический поиск** (Яндекс Вебмастер, Google Search Console) не подключён. Панель показывает статус «не подключено» и не изображает данные.

## 5. Жалобы

Кнопка «⚠️ Пожаловаться» в задании отправляет жалобу. Для этого нужен аккаунт; лимит — 10 жалоб за 10 минут, а одинаковая открытая жалоба не дублируется.

Раньше кнопка только показывала «Жалоба отправлена» и ничего не сохраняла. Поэтому **жалоб до этой версии нет**.

Статусы жалобы: новая, в работе, исправлено, отклонено. Каждое изменение статуса или внутреннего комментария пишется в журнал аудита и видно в истории жалобы.

## 6. Качество обучения

Сигнал — это повод проверить задание, а не утверждение, что оно ошибочно. Пороги меняются в разделе «Управление → Настройки».

| Сигнал | Когда срабатывает |
|---|---|
| Низкая точность | Ниже 15% при минимальной выборке 30 ответов |
| Падение точности | На 25 п.п. и больше относительно прошлого периода; выборка ≥ 30 в обоих периодах |
| Жалобы | 2 и больше открытых |
| Открывают и не отвечают | Доля открытий без ответа ≥ 60% при ≥ 30 открытиях |
| Неполные метаданные | Нет разбора, нет темы, у задания с выбором меньше двух вариантов, статус «нужна проверка» |

## 7. Техническое состояние и оповещения

**Метрики запросов** — паттерн маршрута, статус и время ответа. Они хранятся только в памяти процесса API и обнуляются при перезапуске; на странице так и написано. Секретов, переменных окружения, доступа к файлам или shell и кнопок перезапуска нет.

**Оповещения** вычисляются при открытии страницы, каждый тип не больше одного раза:
- падение решений;
- рост 5xx;
- недоступность БД;
- рост жалоб;
- аномальная точность;
- ошибки входа.

У каждого оповещения есть минимальный объём данных. Внешние каналы (Telegram, почта) **не подключены**, поэтому наружу ничего не отправляется. Сбой импорта API не видит, так как импорт идёт скриптами при деплое.

## 8. Журнал аудита

Таблица `admin_audit_log` хранит, кто, что, над каким объектом, когда, с каким результатом и безопасные детали.

Журнал **только дополняется**: триггер в базе запрещает `UPDATE` и `DELETE`, поэтому даже API не может его переписать.

## 9. Что не восстанавливается задним числом

**Есть за всю историю:**
- регистрации;
- ответы зарегистрированных (верно/неверно, по предметам и номерам);
- DAU/WAU/MAU зарегистрированных;
- пороги 1/5/10/25/50/100;
- удержание D1/D7/D30;
- карточки пользователей;
- статусы заданий.

**Только с момента выкладки:**
- гости (визиты, ответы, начало тренировки);
- воронка посетителей;
- выбор предмета и открытие задания;
- кампании и атрибуция регистраций;
- жалобы;
- брошенные задания;
- технические метрики (с момента запуска процесса).

## 10. Миграция и выкладка

Миграция `0024_admin_analytics` только создаёт новые таблицы и индексы, а также триггер журнала. Существующие данные она не меняет.

`CREATE INDEX attempts_created_idx` на большой таблице `attempts` ненадолго блокирует запись. При текущем объёме это доли секунды; на большой базе индекс стоит создать заранее через `CREATE INDEX CONCURRENTLY` вручную.

Безопасный порядок выкладки:
1. Сделать бэкап БД.
2. Выполнить обычный деплой: `migrate` → `api`.
3. Вписать `ADMIN_OWNER_USER_IDS` и перезапустить `api`.
4. Открыть `/admin`.

Без шага 3 админка просто отвечает «Нет доступа».

Политика конфиденциальности дополнена описанием cookie статистики и хранения жалоб. Перед выкладкой владельцу стоит её проверить.
