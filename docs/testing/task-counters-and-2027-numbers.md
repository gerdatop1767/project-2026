# Счётчики заданий и номера ЕГЭ 2027 Ященко

Дата: 31.10.2026. База: локальная тестовая PostgreSQL 16 с тем же контентом, что в релизе `c98250d`. Production, VPS и боевую базу не трогали.

## 1. Почему счётчики показывали неправильные цифры

У API `GET /tasks/counts` два поля:

| Поле | Что считает |
|---|---|
| `count` | задания «Все источники». Сборник ЕГЭ 2027 туда не входит |
| `countAllSources` | все опубликованные задания |

Экраны брали разные поля, поэтому один и тот же предмет на разных экранах имел разный размер:

| Экран | Было | Поле | Математика |
|---|---|---|---|
| Главная (мобильная), карточки предметов | `count` | без 2027 | **190** |
| Каталог предметов (моб. и десктоп) | `count` | без 2027 | **190** |
| Выбор предмета (`SubjectPicker`) | `count` | без 2027 | **190** |
| Каталог, «N+ заданий» всего | сумма `count` и «+» | без 2027 | **667+** |
| Предмет, «Решено N из M» | `countAllSources` | все | 678 |
| Статистика, «из M» | `countAllSources` | все | 678 |
| Экран входа | захардкожено | — | **«10 000+ заданий по всем предметам»** |

Кроме того, `countAllSources` не проверял, опубликован ли источник задания. Задание, которое лежит только в неопубликованном сборнике вне «Все источники», считалось бы доступным, хотя открыть его нельзя.

## 2. Почему в ЕГЭ 2027 Ященко было 19 номеров вместо 20

Первопричина на frontend, но не в одной точке. Сетку номеров «По номерам» и «Собрать вариант» строил **захардкоженный** `subjectContent.ts` → `taskNumberCount: 19` для математики (формат 2026). Выбранный сборник на сетку не влиял. Backend отдельного списка номеров не отдавал, так что взять реальный было неоткуда.

С данными и запросами всё было в порядке:
- все 25 вариантов: 20 связей, `variant_tasks.position = tasks.task_number`;
- `source_task_number = task_number` у всех 500;
- `GET /tasks?taskNumber=20&collection=ege-2027-yashchenko` возвращал задания.

Без исправления №20 можно было открыть только из полного варианта.

**Найден и исправлен второй дефект:** сессия по одному номеру брала только первую страницу API (20 заданий по умолчанию). Во всех 25 вариантах есть по 25 копий каждого номера. Ученику попадали №N только из вариантов 1–20, варианты 21–25 были недоступны. Теперь клиент запрашивает страницы по 100 и идёт по `nextCursor`. Проверено в браузере: «Задание 1 из 25».

## 4. Как теперь считается количество заданий

Один источник — backend. Определение одно:

> **Доступное задание:** `status = 'published'`, И при этом оно либо в «Все источники», либо входит в опубликованный вариант опубликованного сборника.

Задания со статусом `draft`, `needs_review`, `archived` и задания только из неопубликованных источников не учитываются.

Три разных показателя, они не смешиваются:

| Показатель | Где | Как |
|---|---|---|
| Уникальные задания предмета | `GET /tasks/counts` → `countAllSources` | `count(*)` по `tasks`: каждое задание один раз, сколько бы вариантов на него ни ссылалось |
| Уникальные задания сборника | `GET /collections` → `taskCount` | `count(distinct task_id)` |
| Задания в вариантах (слоты) | `GET /collections` → `variantTaskCount`, у варианта `taskCount` | число опубликованных связей вариант–задание |

Общий счётчик в каталоге — сумма `countAllSources` по предметам. У задания один предмет, поэтому двойного счёта нет.

## 7. Аудит 12 заданий needs_review

У всех 12:
- есть условие, ответ и разбор;
- `$` в формулах парные;
- повреждённого содержимого нет;
- причина записана в `tasks.review_note`.

Подробности в `docs/imports/ege-2027-yashchenko-v1-v25-final-audit.md`, раздел 6.

| Задания | Причина | Вердикт |
|---|---|---|
| В1, В2, В17, В18 №17 | `n` задан только неравенством 0<n<0,5; ответ — формула от n | **оставить скрытыми**: числового ответа нет, автоматическая проверка формулы с параметром ненадёжна |
| В5, В6, В15, В16 №17 | значение R не дано; ответ вида 125√(2R) | **оставить скрытыми**, пока нет сверки со сборником (какое R он подразумевает) |
| В9 №9, В10 №9 | отметка x почти в вершине графика | **оставить скрытыми**: ответ зависит от прочтения рисунка |
| В14 №18 | условие противоречиво (P не на луче BH) | **оставить скрытым** |
| В4 №15 | в условии нет слова «прямая»; 97/99 верно только для прямой призмы | **оставить скрытым** |

Ни одно задание нельзя безопасно опубликовать без внешнего источника: у нас есть сканы условий, но нет ответов сборника. Я не публиковал и не менял ни одно из них.

Как безопасно публиковать позже, по одному заданию:
1. Получить ответы сборника. Сверить ключ.
   - Для №17 с R или n ответ сборника покажет, подразумевается ли конкретное значение. Тогда в условие добавляется именно оно, по сборнику, а не придуманное.
   - Для В4 №15 подтверждение, что призма прямая.
2. Исправить данные в импортёре (`packages/db/src/importEge2027YashchenkoVariantN.ts`): условие, ключ, `status: 'published'`, убрать `reviewNote`. Добавить тест на ключ.
3. На сервере повторно запустить импортёр этого варианта. Это upsert по (вариант, номер): ID задания и прогресс учеников сохраняются.

Для разовой правки без деплоя кода есть админский `POST /admin/content/tasks/:id/status`, он пишет журнал аудита. Но тогда следующий запуск импортёра вернёт `needs_review`, поэтому источник правды — импортёр.

## 9. Обновление production

Миграций и изменений данных нет. Нужен только новый код api и web.

1. Резервная копия БД (`pg_dump`), как в `docs/deployment/pre-deploy-checklist.md` 3.1.
2. Код: `git pull`, `$C build api web`, `$C up -d api web`.
3. Проверка:
   ```bash
   curl -fsS https://zybrilka.ru/api/v1/tasks/counts
   # math: countAllSources 678, taskNumbers 1..19; russian: 477
   curl -fsS https://zybrilka.ru/api/v1/collections | grep -o '"taskNumbers":\[[0-9,]*\]'
   # у ege-2027-yashchenko — 1..20
   ```
   Затем в интерфейсе: Математика → По номерам → «ЕГЭ 2027 Ященко» → видно №20 → открыть, «1 из 25».
4. Откат: прежний коммит, `build` и `up`. Схема та же.

Старый закешированный клиент работает с новым API: новые поля необязательные. Новый клиент со старым API показывает прежние номера через запасной вариант.
