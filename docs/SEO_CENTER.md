Статус: реализовано в ветке `chore/add-emil-design-eng-skill` (ноябрь 2026). Production не затрагивался: ключи — §12, команды для VPS — §13, ограничения — §14.

## 2. Архитектура

```
             ┌───────────── apps/api ─────────────┐
браузер ──►  │ /blog, /blog/:slug, /blog/sitemap.xml│  SSR HTML статей (поисковик получает готовую страницу)
Caddy        │ /api/v1/admin/seo/*  (owner-only)   │  SEO Center: настройки, статьи, семантика, аудит…
             └──────────────┬──────────────────────┘
                            │ PostgreSQL (таблицы seo_*)
             ┌──────────────┴───── apps/worker ────────────────┐
             │ SeoScheduler (раз в минуту): план дня/недели     │
             │ SeoQueue: seo_tasks (lease, retries, idempotency)│
             │ агенты: research · competitor · content · visual │
             │         distribution · analytics · optimization  │
             │         technical · strategy                     │
             │ AiGateway: Claude API, бюджет, учёт токенов, кэш │
             │ интеграции: Webmaster · Metrika · GSC · IndexNow │
             │             Telegram-канал                       │
             └──────────────────────────────────────────────────┘
```

Принципы:
- **Одна очередь задач** `seo_tasks` в Postgres (`apps/worker/src/seo/queue.ts`):
  - `idempotency_key` UNIQUE, захват `FOR UPDATE SKIP LOCKED` — повторно доставленная задача выполняется один раз;
  - аренда 5 мин, которую продлевает heartbeat, пока обработчик жив: медленную задачу другой worker не перехватит; аренда истекает только у упавшего worker, и тогда задача возвращается в очередь;
  - таймаут (15 мин) и «Остановить всё» **отменяют** работу: AbortSignal доходит до запроса к модели и до HTTP-запросов интеграций (`taskScope.ts`), очередь ждёт фактической остановки обработчика и только потом освобождает задачу;
  - повторы: не больше 3 попыток с паузой 1 / 4 / 16 мин; итог записывает только worker, владеющий арендой;
  - статья при ошибке генерации возвращается в прежний статус с причиной (на последней попытке — «Ошибка»); уборка в планировщике снимает «зависшие» статьи без живой задачи.
  - **огороженные записи** (`ctx.commit`): результат задачи (статья, факт-чек, изображения, следующая задача) пишется в транзакции, которая сначала блокирует строку задачи и проверяет, что этот worker всё ещё её владелец. Worker, потерявший аренду, не пишет ничего; heartbeat замечает потерю и прерывает его работу;
  - **условные переходы статусов**: факт-чек и изображения применяются, только если статья всё ещё та же версия и в том же состоянии (ручная публикация или правка во время работы агента не затираются); «Применить обновление» забирает ревизию одним условным UPDATE — двойное применение невозможно; правка в админке передаёт версию открытой статьи и получает 409, если статью сохранили раньше.
- **Агенты — модули, а не процессы.** Каждый тип задачи (`research`, `write_article`, …) обрабатывается своим модулем со своим промптом и контекстом.
- **Код управляет циклом, модель — содержанием.** Порядок шагов, лимиты и публикация решаются кодом; модель исследует, пишет, оценивает. Бесконечный цикл генерации невозможен: каждая задача создаёт только задачи следующего этапа, суточные лимиты в настройках.
- **Никаких выдуманных цифр.** Метрики берутся только из подключённых источников, иначе API отдаёт `null`, а интерфейс — «Нет данных».

## 3. AI-слой (`apps/worker/src/seo/ai.ts`)

- Claude API через официальный SDK `@anthropic-ai/sdk`.
- Модели по ролям (меняются в настройках): **Claude Opus 5.5** — статьи, стратегия, факт-чек; **Claude Haiku 5.5** — классификация, кластеризация, проверка структуры, поиск дублей.
- Исследование — серверный инструмент `web_search` (официальный, Anthropic выполняет поиск). Обходов защит, скрейпинга закрытых страниц и CAPTCHA нет.
- Структурированные ответы — `output_config.format` (JSON Schema), ответ дополнительно проверяется Zod.
- **Бюджет — атомарное резервирование** перед КАЖДЫМ запросом к API (включая продолжения `pause_turn`): под advisory-блокировкой Postgres суммируются расходы и открытые резервы всех задач и worker, и вставляется резерв на худшую стоимость запроса (вход без кэша + 25 000 токенов на каждый веб-поиск, полный `max_tokens`, все поиски). Не помещается — запрос не делается, задача получает статус «остановлена» (`budget_daily`/`budget_monthly`) без траты попыток. После ответа резерв заменяется фактической стоимостью. Прерванный запрос (таймаут, остановка, обрыв сети) записывается по реальным частичным данным потока (входные токены из `message_start` + оценка уже полученного вывода); отказ API (HTTP 4xx/5xx до генерации) — 0; обрыв до первого события — оценка стоимости ввода. Отмена через AbortSignal закрывает HTTP-соединение (проверено тестом на настоящем SDK), поэтому генерация на стороне API прекращается. Резерв упавшего worker остаётся по худшей стоимости и через час помечается `abandoned`.
- **Учёт:** каждый вызов пишется в `seo_ai_usage` (модель, агент, токены вход/выход/кэш, стоимость, поисковые запросы).
- **Кэш:** результаты исследований хранятся в `seo_research_cache` по хешу запроса (TTL по типу), повторная работа не выполняется.

## 5. Цикл агента

**Ежедневно** (время из настроек, Москва):
1. `sync_metrics` — Вебмастер, Метрика, GSC за последние дни (идемпотентно, upsert).
2. `research` — поиск тем и запросов (web_search + семантика + база знаний), запись идей и ключей.
3. `score_topics` — оценка идей (дешёвая модель + формула), проверка каннибализации.
4. `write_article` × N (N = «статей в день», только темы выше порога приоритета).
5. `review_article` — факт-чек и проверка качества сильной моделью; не прошла — «На проверке» с замечаниями.
6. `visuals` — SVG-обложка и инфографика из данных статьи.
7. `publish` — только в автономном режиме, не раньше времени публикации и при выключенной паузе. Публикация идемпотентна (уникальный slug + статус). После публикации: sitemap обновляется сам (строится из БД), пинг IndexNow, проверка доступности и canonical.
8. `distribute` — адаптированные материалы для площадок; автоматически только через разрешённые API (Telegram-канал бота), остальное — «готово к ручной публикации».

**Еженедельно:** `technical_audit`, `competitors`, `weekly_strategy` (анализ эффективности → `seo_learning_log` + `seo_insights` → обновлённые веса тем и план недели), `refresh_articles` (статьи, потерявшие позиции → «Требует обновления»).

**Режимы:** ручной (идеи и черновики, ничего не публикует), полуавтоматический (пишет; публикация — после одобрения в админке), автономный (публикует сам, но с лимитами бюджета, качества и количества).

**Аварийная остановка:** одна кнопка ставит `emergency_stop`. Планировщик ничего не создаёт, очередь ничего не берёт, AI-шлюз отказывает в вызовах.

## 6. Оценки

**SEO-приоритет темы** (0–100): спрос 25 %, конкурентность (обратно) 15 %, сезонность 10 %, актуальность 10 %, соответствие Зубрилке 15 %, потенциал регистраций 15 %, шанс на ТОП 10 %. Каждый фактор 0–10 приходит от модели с обоснованием; вес факторов корректирует еженедельная стратегия по реальным данным (`seo_settings.priority_weights`).

**SEO Score статьи** (0–100) считается только из реальных метрик за 28 дней: показы, клики, CTR, средняя позиция, визиты из поиска, регистрации (кампания статьи). Нет данных → `null`, а не 0.

## 7. Статьи на сайте

- URL: `https://zybrilka.ru/blog/<slug>`; список `/blog`; `sitemap` блога `/blog/sitemap.xml` (подключён в `robots.txt`).
- Серверный рендеринг в API: title, description, canonical, OG, JSON-LD (`Article` + `FAQPage` + `BreadcrumbList`), содержание, FAQ. Markdown рендерится собственным безопасным рендерером (весь текст экранируется, ссылки только http(s) и относительные).
- Ссылки на тренажёр идут через кампанию статьи (`/api/v1/go/seo-<slug>`) → переходы и регистрации на статью считаются существующей атрибуцией.
- Неопубликованная статья отдаёт 404. Повторная публикация невозможна: публикация — атомарный переход `scheduled/review → published` одним UPDATE с условием на статус.

## 8. Внешние площадки

| Площадка | Автоматически | Как |
|---|---|---|
| Telegram-канал | да | Bot API `sendMessage`, бот должен быть админом канала (`TELEGRAM_SEO_CHANNEL_ID`) |
| VK | нет (нужен токен сообщества с правом `wall`) | архитектура готова, сейчас — ручной пакет |
| Дзен, VC.ru, Pikabu, Reddit, форумы | нет (нет разрешённого API публикации для таких аккаунтов) | агент готовит адаптированный текст, ссылку с кампанией и чек-лист правил площадки; админ публикует руками и отмечает «опубликовано» с URL |

Одинаковый текст на разных площадках запрещён: перед сохранением сравнивается шинглами с другими постами той же статьи (порог сходства 0,6).

## 10. Что сознательно не делается

- Нет генерации фотореалистичных картинок и копирования мемов из интернета: авторские права. Обложки и инфографика — оригинальные SVG из данных статьи; мем-карточки — оригинальные подписи на фирменном фоне (без чужих шаблонов).
- Нет автоматической публикации там, где нет разрешённого API; нет фейковых аккаунтов, отзывов и ссылочных схем.
- Статьи с утверждениями об ЕГЭ проходят факт-чек; непроверенное → «На проверке», а не «Опубликована».

## 14. Ограничения и что проверить

- **Яндекс Вебмастер API.** Документация API v4 была недоступна из среды разработки, поэтому пути и имена полей клиента (`apps/worker/src/seo/integrations/clients.ts`, класс `YandexWebmaster`) написаны по знанию API v4 и не сверены с актуальной документацией. При первом подключении нажмите «Проверить»: если формат отличается, ошибка API будет показана дословно, а исправление сводится к одному файлу. Метрика, Search Console, IndexNow, Telegram и VK используют хорошо известные стабильные эндпоинты, но с реальными токенами их тоже никто ещё не проверял.
- **Частотность запросов.** Официального API Wordstat в проекте нет. Реальная частотность берётся только из CSV-импорта, а показы — из Вебмастера и GSC. Оценки модели хранятся отдельно (`demandEstimate`) и не выдаются за частотность.
- **Core Web Vitals** не измеряются: нужен PageSpeed Insights API (ещё один ключ). Аудит меряет время полного ответа сервера.
- **Дзен, VC.ru, Pikabu, Reddit:** только подготовка материала и чек-лист правил. Публикует человек и отмечает в админке URL поста.
- **Изображения:** только оригинальные SVG (обложка, инфографика, мем-карточка с собственной подписью). Фото-генерации нет. Загружать свои PNG, JPEG или WebP можно в карточке статьи, указав лицензию.
- **Отказ модели** (`stop_reason: refusal`) завершает задачу ошибкой без повторов. Автоматическое переключение на запасную модель не включено.
- **«Самообучение»** — это пересчёт базы знаний и весов приоритета по реальным метрикам. Минимум 8 статей с данными, вес меняется не больше чем на 20 % в неделю. Пока данных мало, агент пишет в журнал «Недостаточно данных» и ничего не меняет.
