### 0bis.3 — Сравнение цифровых ответов (`checkAnswer`)

Реализовано **точечное, опциональное** расширение `packages/shared/src/answerChecker.ts`, не меняющее поведение по умолчанию ни для одного существующего ответа (математика включительно):

Если флаг не передан (или `false`) — поведение **побайтово идентично** прежнему: конкатенированная цифровая строка ("134") сравнивается как есть, без перестановок — ничего не меняется молча для существующих заданий.

- Эта опция сейчас **не подключена** к `submitAttempt` автоматически — потому что ни в схеме `tasks`, ни в DTO сейчас нет поля, которое говорило бы "у этого конкретного задания допустим любой порядок цифр" (это решение по заданию, а не по типу ответа в целом). - Добавлены тесты (`packages/shared/src/answerChecker.test.ts`): дефолтное поведение не изменилось ("134" vs "431" → false без флага); явный флаг принимает любую перестановку одного и того же набора цифр; флаг не трогает нецифровые/разделённые пробелом ответы; граничные случаи (разная длина, разный набор).

### Найденный, но НЕ исправленный архитектурный нюанс: order-insensitive цифровые ответы

Официальный формат ответа ЕГЭ на задания типа "запишите номера ответов" — слитная строка цифр (например, `"134"`), которую по правилам допустимо вводить **в любом порядке**. Текущий `checkAnswer` (`packages/shared/src/answerChecker.ts`) поддерживает order-insensitive сравнение только для **разделённых пробелом/точкой с запятой** токенов (`"1 3 4"` vs `"3 1 4"` — ОК), но **не** для слитной строки (`"134"` vs `"314"` — это один токен, сравнивается как есть, НЕ как набор цифр). Для всех 19 математических вариантов это никогда не всплывало (там таких заданий с multi-select ответом нет), но для русского это будет актуально для реальных студентов, если они введут цифры не в том порядке, что в ключе.

**Я не стал молча это обходить** (например, через костыль с автосортировкой при импорте) — это требует решения: либо расширять `checkAnswer` с новым режимом "цифровой набор", либо писать на фронтенде отдельный ввод "отметь варианты" вместо текстового поля для этих заданий. Оставляю как явный открытый пункт.

**Обновление:** `checkAnswer` теперь поддерживает опциональный, явно запрашиваемый режим `digitSetOrderInsensitive` (см. §0bis.3) — реализация готова и протестирована, но **не подключена автоматически** ни к одному заданию, так как решение "какому конкретному заданию разрешён любой порядок цифр" требует отдельного поля в схеме `tasks` (небольшая, но отдельная аддитивная миграция), которую я не стал делать без вашего отдельного решения — это всё ещё открытый пункт, просто с готовым, протестированным "строительным блоком" для его решения.
