# Аудит безопасности Zybrilka — ноябрь 2026

Ветка `chore/add-emil-design-eng-skill`, состояние кода на 14.11.2026.
Аудит проводился по исходному коду и на локальном стенде (тестовая база, API, production-сборка сайта).
Production-сервер, его настройки и данные не трогались: не подключались к VPS, не запускали нагрузочные тесты, не меняли `.env`, Docker Compose, миграции и данные.

## 1. Общая оценка

**Базовая защита построена хорошо.**
- Сессии хранятся на сервере, cookie недоступна скриптам.
- Telegram-вход проверяется по подписи.
- Чужие данные закрыты фильтром по владельцу.
- Админка доступна только владельцам.
- Загрузки файлов проверяются.
- Внутренние порты закрыты.

**Найдено подтверждённых проблем: 4.**
- Утечка текста SQL-запросов в ответах с ошибкой 500.
- Отсутствие заголовков безопасности: нет защиты от встраивания в чужие страницы (clickjacking), нет HSTS и nosniff.
- Возможность накрутки опыта и рейтинга скриптом.
- Уязвимые версии `zod` и `fastify` в работающем API.

**Найден один потенциальный риск: 1.** Слепой SSRF через редирект при загрузке аватара провайдера.

Всё перечисленное, кроме части про накрутку, исправлено и покрыто тестами. Накрутка ограничена по скорости, а правило начисления опыта требует решения владельца (раздел 9).

**Критических уязвимостей, позволяющих войти в чужой аккаунт или прочитать чужие данные, не найдено.**

Мы **не заявляем, что сайт полностью защищён**. Не проверялись:
- настройки живого сервера: TLS, файрвол, SSH, резервные копии на VPS;
- работа под реальной нагрузкой;
- внешние сервисы: Telegram, VK, Яндекс.

## 3. Как можно было эксплуатировать

**1. Утечка SQL.**
- Любая ошибка базы, например при несовпадении схемы после неудачного деплоя или при необычном запросе, возвращалась клиенту так: `{"message":"Failed query: select … from tasks … params: published,math,…"}`.
- Мы воспроизвели это на стенде: при отставшей схеме `GET /api/v1/tasks/random` отдавал полный текст запроса.
- Злоумышленник узнаёт имена таблиц и колонок, параметры запросов, а в худшем случае — идентификаторы пользователей. Это облегчает другие атаки.

**2. Накрутка.**
- Схема для бота с одним реальным аккаунтом (Telegram, VK или Яндекс):
  1. отправить в задание заведомо неверный ответ;
  2. получить в ответе `correctAnswer`;
  3. отправить его и получить полный опыт «за первое решение».
- Раньше лимита на ответы вошедших пользователей не было вообще, поэтому весь банк заданий (≈3000) проходился за минуты. Аккаунт поднимался на первое место рейтинга.
- Опыт за одно задание дедуплицируется, поэтому бесконечной накрутки нет. Но весь банк можно «решить» без единого настоящего решения.

**3. Заголовки.**
- **Clickjacking:** сайт можно было встроить в невидимый iframe на чужой странице и заставить ученика нажать кнопку, например «удалить ошибку» или «выйти».
- **MIME-sniffing:** браузер мог интерпретировать файл не так, как задумано.
- **HTTP-перехват:** без HSTS первое обращение по http можно перехватить в публичной Wi-Fi-сети.

**4. Зависимости.**
- `zod < 4.6.6` может исчерпать память на огромных коллекциях при валидации. Удалённо это ограничено лимитом тела запроса в 1 МБ, но риск реальный.
- `fast-uri` подменяет схему и хост в URI.
- `fastify` обходит проверку заголовков из-за регистра.

**5. SSRF.**
- URL аватара приходит от провайдера: Telegram, VK или Яндекс.
- Если бы на разрешённом хосте был открытый редирект, сервер при `redirect: 'follow'` сходил бы на внутренний адрес, например `http://postgres:5432/`, прежде чем проверить конечный URL.
- Ответ пользователю не возвращается (это «слепой» запрос), поэтому вероятность и ущерб низкие.

## 4. Что исправлено

| № | Исправление |
|---|---|
| 1 | Глобальный обработчик ошибок API. 5xx отвечает `{"error":"internal_error"}`, а полная ошибка пишется только в лог сервера. Ответы 4xx не изменились (тот же формат, 429 и т. п.); у админки свой обработчик, как и раньше. |
| 2 | Лимит ответов на задания: 60 в минуту на аккаунт, гости — 120 в минуту на IP, как было. Ученик тратит на ответ секунды и больше, вариант — 19–27 ответов, поэтому лимит обычным пользователям не мешает. Скрипту теперь нужно ≥ 50 минут на банк вместо минут. |
| 3 | **API:** на каждый ответ ставятся `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=31536000`. |
| 3 | **Сайт (nginx):** `nosniff`, `Referrer-Policy`, HSTS, `Permissions-Policy` (камера, микрофон, геолокация и оплата отключены). `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org https://*.telegram.org; object-src 'none'; base-uri 'self'`: встраивать сайт могут только он сам и Telegram Web (там Mini App открывается в iframe). Заголовки повторены в каждом `location`, иначе nginx их отбрасывает. |
| 4 | `zod` 4.6.5 → 4.6.7, `fastify` 5.12.5 → 5.12.8, `fast-uri` → 3.1.9 / 4.2.3 (транзитивно). Для разработки: `vite` → 8.3.8, `vitest` → 5.1.0, `undici` → 8.12.4, `source-map-js` → 1.2.2. Только патч-версии, кроме `vitest` (dev-инструмент; minor-версию потребовала связка с `@testing-library/jest-dom`). |
| 5 | Редиректы аватара проходятся вручную: не больше 3, каждый шаг должен вести на разрешённый хост. Тело читается потоком с жёстким лимитом размера, даже без `content-length`. |

## 6. Проведённые проверки

**Код и конфигурация.**
- **Авторизация и сессии.**
  - `session_id`: случайный UUID (122 бита), cookie `httpOnly`, `Secure` в production, `SameSite=Lax`.
  - Срок жизни 30 дней; выход удаляет сессию на сервере; есть смена сессии при входе.
  - Заголовок `x-anon-id` в production не принимается, пользователь берётся только из сессии.
- **Telegram.**
  - Проверка initData по HMAC (`WebAppData`) с `timingSafeEqual`.
  - Проверка срока `auth_date` и даты из будущего.
- **VK и Яндекс.**
  - OAuth со `state` и PKCE (случайные 16 байт).
  - Переход из Mini App во внешний браузер — через одноразовые токены, в базе хранятся их хеши.
- **Пароли.**
  - Вход по паролю удалён. Оставшиеся в схеме таблицы содержат только scrypt-хеши и хеши токенов, кодом не используются.
  - Паролей в открытом виде нет.
- **IDOR.** Все маршруты с id (ошибки, избранное, сессии и попытки вариантов, профиль) фильтруют по `userId` из сессии; чужой id даёт 404.
- **SQL-инъекции.** Drizzle с параметрами. `sql.raw` используется только с константами или белым списком (`ASC`/`DESC`, часовой пояс).
- **XSS.** React экранирует вывод. Markdown теории превращается в React-элементы, не в HTML. KaTeX работает с `trust: false`. Загруженные изображения отдаются с `nosniff` и sandbox-CSP.
- **CSRF.**
  - Cookie `SameSite=Lax`.
  - Все записи отклоняются при `Sec-Fetch-Site: cross-site`.
  - Для записей в админке нужен отдельный заголовок.
- **CORS.** Плагин не подключён, ответы не разрешают чужие источники.
- **Админка.**
  - Доступ только владельцам из `ADMIN_OWNER_USER_IDS`.
  - Отказы пишутся в журнал аудита.
  - Импорт заданий не доступен по HTTP: это офлайн-скрипты с проверкой.
- **Загрузки.** Аватары и картинки рассылок проверяются по сигнатуре (JPEG/PNG/WebP) и размеру.
- **Лимиты.**
  - Вход: 20–30 за 10 минут.
  - Жалобы: 10 за 10 минут на аккаунт.
  - Аналитика: 60 в минуту.
  - Напоминания и мини-игры — свои лимиты на аккаунт.
  - Тело запроса — до 1 МБ (по умолчанию).
- **Инфраструктура (по файлам).**
  - PostgreSQL, API и web не публикуют портов, наружу смотрит только Caddy (80/443).
  - Секреты берутся из `.env`, в git только `.env.example`.
  - В bundle сайта нет токенов и паролей.
  - Caddy получает TLS-сертификаты автоматически. Его собственные настройки (TLS-версии, шифры) на живом сервере не проверялись.
- **Зависимости:** `pnpm audit` до и после обновления.

## 7. Что не исправлено и почему

- **Правило опыта после показа ответа.** Сейчас после неверного ответа сервер показывает верный, и повторный правильный ответ даёт полный опыт. Как это изменить — продуктовое решение (раздел 9).
- **Хеширование токенов сессий** требует миграции схемы. Без отдельного согласования миграции не запускаем.
- **«Выйти на всех устройствах»** — новая функция, а не исправление.
- **CSP для скриптов.** Нужен список разрешённых источников, проверенный на живом сайте: Метрика, Telegram SDK, VK ID, inline-скрипт темы. Строгая политика без проверки может сломать вход и аналитику. Сейчас включена безопасная часть: `frame-ancestors`, `object-src`, `base-uri`.
- **Уязвимости dev-инструментов** (eslint → `zod`/`minimatch`, drizzle-kit → `esbuild`) в production-образ не попадают. Их исправление — обновление самих инструментов, отдельной задачей.

## 9. Рекомендации

1. **Опыт после показа ответа (решение владельца).** Варианты:
   - (а) первое решение даёт опыт, только если верным был **первый** ответ на это задание;
   - (б) после показа ответа за задание даётся уменьшенный опыт, как за повторение;
   - (в) верный ответ показывать только после 2 попыток.

   Рекомендуем (а) или (б): они не мешают ученикам и закрывают накрутку.
2. **Рейтинг.** Сделать фильтр аномалий: десятки первых решений в минуту, почти 100% точность на сотнях заданий за день — помечать для проверки в админке.
3. **Токены сессий.** Хранить в базе SHA-256 токена вместо самого токена (миграция плюс перевыпуск сессий при входе).
4. **«Выйти на всех устройствах»** в профиле; это уже реализовано для админа.
5. **Поддержка в боте.** Ограничить, например, до 30 сообщений за 10 минут на чат: лишние не сохранять и один раз ответить «слишком много сообщений».
6. **CSP.** Включить сначала `Content-Security-Policy-Report-Only` со списком источников, собрать отчёты, затем перевести в обязательный режим. Inline-скрипт темы — через хеш.
7. **Остатки входа по почте.** Убедиться, что в таблицах нет актуальных данных, удалить данные, затем таблицы — отдельной миграцией.
8. **Сервер (проверить на VPS).**
   - Файрвол: открыты только 22/80/443.
   - SSH только по ключам.
   - Автообновления безопасности ОС.
   - Резервные копии PostgreSQL зашифрованы и хранятся вне сервера; восстановление проверено.
   - Ротация логов Docker.
9. **Зависимости.** Регулярно запускать `pnpm audit --prod` в CI. Обновить eslint и drizzle-kit до версий без уязвимых транзитивных пакетов.
10. **CAPTCHA сейчас не нужна.** Аккаунт создаётся только через Telegram, VK или Яндекс — это уже сильная защита от массовой регистрации. Если появится вход по почте или паролю, добавить Яндекс SmartCaptcha на регистрацию и сброс пароля.

## 10. Защита от спама, перебора и массовых атак

| Сценарий | Защита |
|---|---|
| Перебор паролей, credential stuffing | Паролей нет: вход только через Telegram, VK, Яндекс. Подбирать нечего. |
| Массовая регистрация | Аккаунт создаётся только подтверждённым входом провайдера. Лимиты на старт входа — 20–30 за 10 минут с IP. |
| Подбор сессии | 122 бита случайности, проверка формата до запроса в базу. Перебор нереален. |
| Массовые ответы, накрутка рейтинга | **Исправлено:** 60 в минуту на аккаунт, 120 в минуту на IP для гостей. Опыт за задание дедуплицируется. Правило после показа ответа — рекомендация 1. |
| Спам жалоб | 10 за 10 минут на аккаунт; дубликаты одной жалобы не сохраняются. |
| Спам в поддержку (бот) | Уведомление владельцу одно на «непрочитанный отрезок», лимиты Telegram. Без ограничения числа сохраняемых сообщений — рекомендация 5. |
| Накрутка достижений, серии | Начисление только на сервере по проверенным ответам, уникальные ключи начислений. |
| Тяжёлые запросы, простые DoS | Тело до 1 МБ, аватары до лимита. Отчёты админки — только владельцу и с лимитом. Публичные маршруты чтения — без тяжёлых операций. Нагрузочное тестирование не проводилось (по условиям задачи). |
| Мини-игры, аналитика, напоминания | Свои лимиты на аккаунт или IP. |

**Итог:** базовая защита от массовых атак на уровне приложения есть. Главный пробел — накрутка ответов — закрыт по скорости; правило опыта ждёт решения. Защиту на уровне сети (DDoS, лимиты в Caddy) мы не проверяли и не меняли.

## 11. Безопасность паролей и пользовательских данных

- **Пароли.** Действующих паролей нет. Исторические scrypt-хеши (если остались) не используются (рекомендация 7). Токены входа и передачи сессии хранятся как хеши.
- **Сессии.** Cookie недоступна JavaScript, передаётся только по HTTPS, не отправляется с чужих сайтов. В базе — открытый id (рекомендация 3).
- **Чужие данные.** Прочитать или изменить чужие попытки, ошибки, избранное, историю вариантов или профиль через подмену id нельзя: все запросы фильтруются по владельцу из сессии, чужое отвечает 404. Это проверено в коде и существующими тестами владения.
- **Рейтинг** показывает только имя и аватар, без контактов и id провайдеров.
- **Логи.** Пишут метод, путь и статус, без тел запросов, cookie и токенов. После исправления 1 внутренние ошибки попадают только в лог сервера.
